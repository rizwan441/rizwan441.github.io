01 · Problem

Manual operations don't scale past a handful of servers

A telecom platform runs on a fleet of production servers, grouped into clusters for different customers. Each cluster mixes web, telephony and database servers. Every software update, configuration change or reboot meant logging into each server one by one, running the step and checking the result by eye.

With over a hundred servers, this was slow and easy to get wrong. Worse, when something failed, there was no quick way to tell why. Was the server down? Were the credentials wrong? Did the script crash? Or was the failure expected, as with a reboot?

Ambiguous failures

A server that was down, a rejected login and a crashed script all looked identical. Every failure needed a manual investigation.

Reboots looked like failures

A reboot drops the connection by design, so successful reboots were reported as broken and had to be checked by hand.

Inventory drift

The server list drifted from reality. Retired servers stayed in it, and moved servers appeared in two places.

No guardrails

Anyone with access could run any command as root on every server, and servers under maintenance were not protected.

02 · Requirements

What the system had to do, and how well

Functional

  • Run an operation on one server, a cluster, or any selection.
  • Stream live output for every server to the browser.
  • Give every server a specific final result with a reason.
  • Handle reboots as a tracked operation, not a failure.
  • Keep the inventory in sync with a single source of truth.
  • Monitor CPU, memory and disk across the fleet.

Non-functional

  • Reliability: one bad server must never block or hide the others.
  • Bounded load: limit how many servers are worked on at once.
  • Resilience: a job keeps running if the operator closes the browser.
  • Security: role-based access and a full audit trail.
  • Safety: a bad input must never wipe the inventory.
03 · High-level design

One orchestration service between operators and the fleet

No agent is installed on the servers. A single backend service connects over SSH, which every server already supports. That keeps the fleet untouched and puts all the logic in one place.

● green: healthy● yellow: in a tracked reboot● red: unreachable
04 · Core idea

A state machine per server, ending in one clear result

Instead of reading an exit code as pass or fail, every server in a job is tracked through explicit states. The dashboard and the final report both read from these states.

05 · Deep dives

The decisions that made it reliable

255

Failure classification

The SSH client returns the same exit code for almost every network problem, so the code alone can't explain a failure. The service reads the error output and matches known patterns: timeouts, refused connections, rejected logins, dropped sessions. Each failure becomes a specific result with a short reason in plain language.

// simplified match stderr { s if s.contains("timed out") => Unreachable("connection timed out"), s if s.contains("Connection refused") => Unreachable("port refused"), s if s.contains("Permission denied") => AuthFailed("login rejected"), _ => Failed(exit_code), }

Why: operators act on the reason, not the code. "Port refused" and "wrong password" need completely different fixes.

id

Verified reboots

Before a reboot, the service records the server's boot ID, which the kernel generates fresh on every start. It sends the reboot in the background, waits for the server to go down, then polls until it answers with a new ID. Unreachable servers are never sent a reboot. Servers that don't return within 10 minutes are flagged.

# before and after $ cat /proc/sys/kernel/random/boot_id 3f2a8d1e-…-c91e # recorded # … server goes down, comes back … a7b04c22-…-15d0 # changed → REBOOTED

Why: "it answers again" isn't proof it restarted. A changed boot ID is proof, and it also catches a reboot that was accepted but never happened.

20

Bounded concurrency

Each server runs as its own async task, but a semaphore keeps at most 20 operations in flight. Health checks have a separate limit. One slow or failing server never blocks the others, and the service never opens hundreds of connections at once.

Why: fleet-wide operations need to be fast without overloading the service or the network.

ws

Jobs that outlive the browser

Output from every server in a job flows into one stream. The stream is saved to the job log and sent to every connected viewer. Closing the tab doesn't stop a job, and reopening it shows the full history so far. Every finished job is written to an audit log.

Why: a reboot across a cluster can take minutes, and a network drop on the operator's side shouldn't affect it.

⇄

Inventory reconciliation

The inventory syncs from a single source of truth. Each sync adds new servers, reassigns moved ones, removes retired ones, and rejects invalid or duplicate entries with a reason. Every sync returns a change report.

Why: automation is only as good as its target list. A safeguard stops a sync from deleting anything when the source comes back empty or unreadable.

rbac

Guardrails

Operators can run approved operations and tracked reboots. Only admins can run arbitrary commands or open a terminal. Clusters in maintenance are skipped automatically. Credentials are encrypted at rest and never exposed in the process list.

Why: a tool that can reboot a whole fleet in one click needs limits that don't rely on people being careful.

Outcomes

  • Fleet-wide operations run from one screen instead of server by server.
  • Successful reboots are verified and show their downtime.
  • Every failure states its cause, so no log digging is needed.
  • The inventory stays accurate automatically.
  • Risky actions are limited by role and by maintenance mode.

How it was validated

  • Disposable containers reproduced each failure type: refused, timed out, rejected login, and a connection killed mid-operation.
  • A simulated restart tested the full reboot lifecycle end to end.
  • Unit tests cover inventory reconciliation, including the empty-source safeguard.

09 · Next steps

Where the design goes next

Rolling deploys

Update one server, verify its health, then continue to the rest of the cluster automatically.

Durable jobs

Save job state so in-progress work survives a service restart.

Key-based access

Replace passwords with SSH keys and verify host keys properly.

Horizontal scale

Move jobs onto a queue so several workers can share the load.
